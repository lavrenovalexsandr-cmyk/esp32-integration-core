# Архитектура экосистемы ESP32: идентификация, профили и управление прошивками

**Назначение:** единый межпроектный архитектурный документ экосистемы ESP32. Он описывает контракты и границы ответственности между прошивками, ESP32 Manager и специализированными интеграциями Home Assistant. Внутреннее устройство ESP32 Platform Core описывается отдельно в его репозитории.

**Статус:** основные решения согласованы. MQTT-профиль реализован и проверен на прошивке Xiaomi BLE Gateway и интеграциях Home Assistant. Очистка retained-профиля перед OTA реализована в ESP32 Manager и проверена на реальном устройстве. Описанные ниже правила для каталога репозиториев и выбора релизов являются согласованными требованиями к дальнейшей реализации.

## 1. Назначение и модель устройства

В экосистеме могут существовать независимые прошивки ESP32: BLE-шлюзы, контроллеры ворот, освещения и другие продукты. ESP32 Manager управляет физическими ESP32 независимо от назначения и установленной прошивки. Специализированные интеграции Home Assistant работают только с устройствами, подходящими для соответствующего продукта.

Различаем три понятия:

- **Физическое устройство** — конкретная ESP32 с постоянной аппаратной/платформенной идентичностью. OTA-перепрошивка не меняет её идентификатор.
- **Продуктовый профиль** — тип приложения, которое в данный момент работает на устройстве.
- **Возможности (capabilities)** — функции, которые объявляет конкретная прошивка.

Профиль не является аппаратной моделью. Не следует подменять им manufacturer или model физического устройства в Home Assistant.

## 2. Границы ответственности

### ESP32 Platform Core

- Универсальный платформенный слой: общие сервисы устройства и инфраструктура MQTT/Home Assistant.
- Не содержит логики конкретных продуктов и не знает о Xiaomi, воротах, освещении и других прикладных функциях.
- Не ведёт реестр допустимых `product_id` или `capabilities`.

### Прикладная прошивка

- Определяет собственный `product_id` и набор `capabilities`.
- Является источником истины для текущего продуктового профиля.
- Публикует профиль по MQTT-контракту из раздела 3.
- Может менять профиль устройства при установке другой прошивки.

### ESP32 Manager

- Отображает все обнаруженные ESP32, включая устройства без известного продуктового профиля и устройства со сторонними/старыми прошивками.
- Предоставляет универсальное управление устройствами и OTA.
- Перед началом OTA очищает retained-сообщение профиля, чтобы старый профиль не считался актуальным во время смены прошивки.
- Управляет локальным для установки Home Assistant каталогом репозиториев прошивок и их credentials.
- Не ограничивает выбор прошивки по текущему профилю устройства.

### Специализированные интеграции Home Assistant

- Самостоятельно определяют подходящие устройства по продуктовому профилю и возможностям.
- Не зависят от наличия ESP32 Manager.
- Не создают продуктовые сущности для устройств с неподходящим или отсутствующим профилем.
- Несколько специализированных интеграций могут одновременно обслуживать одно физическое устройство, если его профиль/возможности подходят каждой из них.

## 3. MQTT-контракт продуктового профиля

Отдельный топик профиля не изменяет существующую аппаратную идентификацию в `device/info`:

```text
esp32/<DEVICE_ID>/device/profile
```

Сообщение публикуется в JSON, с QoS 1 и retain=true. Схема версии 1:

```json
{
  "schema_version": 1,
  "product_id": "xiaomi_ble_gateway",
  "firmware_version": "2.0.0",
  "capabilities": [
    "ble_gateway",
    "xiaomi_lywsd03"
  ]
}
```

Обязательные поля:

- `schema_version` — версия формата сообщения.
- `product_id` — стабильный идентификатор продукта, задаваемый прикладной прошивкой.
- `firmware_version` — версия работающей прикладной прошивки; должна совпадать со значением `sw_version` в `device/info`.
- `capabilities` — массив строк с возможностями прошивки. Пустой массив допустим.

Примеры идентификаторов (не закрытый реестр):

| Прошивка | product_id | capabilities |
|---|---|---|
| Xiaomi BLE Gateway | `xiaomi_ble_gateway` | `ble_gateway`, `xiaomi_lywsd03` |
| Gate Controller | `gate_controller` | `gate_control` |
| Light Controller | `light_controller` | `light_control`, `dimming` |

### Публикация и жизненный цикл

- Прошивка публикует актуальный профиль при первом подключении к MQTT и повторно после каждого MQTT reconnect.
- Профиль публикуется как retained-сообщение с QoS 1.
- Перед OTA ESP32 Manager публикует пустое retained-сообщение в `esp32/<DEVICE_ID>/device/profile` (MQTT tombstone).
- После успешной загрузки новая прошивка публикует свой профиль.
- Если новая прошивка не запускается и устройство загружает прежнюю прошивку, прежняя прошивка при старте/reconnect публикует свой профиль снова.
- Устройство без продуктового профиля не публикует сообщение профиля; отсутствие retained-сообщения означает отсутствие известного профиля.

### Валидация

- Неизвестный `schema_version`, некорректный JSON или отсутствие обязательных полей — профиль не используется.
- Несовпадение `firmware_version` и `sw_version` из `device/info` означает, что профиль неактуален и не должен использоваться до получения согласованных метаданных.
- Неизвестный `product_id` игнорируется интеграциями, которые его не поддерживают.
- Неизвестная отдельная capability не должна мешать обработке других поддерживаемых возможностей.

## 4. Смена профиля и сущности Home Assistant

Смена профиля не меняет идентификатор физической ESP32 и не должна удалять общую запись устройства в Device Registry.

При смене профиля:

- Сущности специализированной интеграции, профиль которой больше не подходит устройству, становятся недоступными.
- Интеграция, которой соответствует новый профиль, обнаруживает устройство и создаёт/обновляет свои сущности.
- Если прежний профиль появляется снова, прежняя интеграция восстанавливает доступность ранее созданных сущностей.
- Автоматическое удаление старых сущностей не выполняется; при необходимости пользователь удаляет их вручную.
- Временное отсутствие профиля после очистки retained перед OTA также означает недоступность соответствующих продуктовых сущностей, а не их удаление.

Поведение при полном исчезновении устройства из MQTT/потере связи определяется общими правилами availability интеграций.

## 5. Обнаружение и хранение профиля в Home Assistant

- Retained-сообщение MQTT `esp32/<DEVICE_ID>/device/profile` — источник истины о текущем продуктовом профиле. Постоянное дублирование профиля в хранилищах Home Assistant не требуется.
- Каждая специализированная интеграция самостоятельно подписывается на wildcard-топик `esp32/+/device/profile` через штатный MQTT API Home Assistant.
- После подписки брокер доставляет последнее retained-сообщение для каждого подходящего топика.
- Полученные профили и состояние их актуальности хранятся в runtime-контексте соответствующего ConfigEntry. Это временное состояние процесса; после перезапуска оно восстанавливается из retained MQTT.
- Конкретный способ хранения runtime-кэша выбирается с учётом поддерживаемого API Home Assistant; нельзя предполагать наличие `ConfigEntry.runtime_data` во всех поддерживаемых версиях.
- Device Registry хранит общую физическую идентичность ESP32 (например, идентификатор платформы `esp32` и постоянный `DEVICE_ID`). Продуктовый профиль не меняет идентификатор устройства.
- Entity Registry хранит сущности специализированных интеграций и их стабильные `unique_id`. Смена профиля сама по себе не удаляет записи сущностей.
- Получение tombstone удаляет профиль из runtime-кэша интеграции и делает соответствующие продуктовые сущности недоступными.
- При потере MQTT-соединения интеграция не должна бесконечно считать ранее полученный профиль актуальным. До восстановления подписки профиль считается неизвестным/неактуальным, а зависящие от него сущности — недоступными.
- После восстановления соединения брокер повторно доставляет retained-профили. Потеря соединения не удаляет записи Device Registry или Entity Registry и не должна создавать дубликаты.

## 6. Универсальный OTA и каталог репозиториев

### Общие правила

ESP32 Manager должен позволять выбрать для любого обнаруженного устройства любой репозиторий и любой доступный релиз прошивки.

- Выбор репозитория и релиза относится к текущей операции OTA и не закрепляется за устройством как постоянное назначение.
- Несовпадение `product_id` текущей прошивки и устанавливаемой прошивки не блокирует OTA. Допустимо показать предупреждение, но не запрещать установку.
- Автоматическая фильтрация репозиториев или релизов по `product_id` не выполняется.
- При выборе релиза ESP32 Manager получает URL подходящего OTA-артефакта и подставляет его в существующее поле URL прошивки.
- Существующее поле URL остаётся доступным для ручного ввода и прямого OTA без выбора релиза.
- Существующие поля и сценарии OTA, включая ручной ввод GitHub-токена, сохраняются.

### Каталог репозиториев

Каталог ведётся локально в конкретной установке Home Assistant; централизованный общий реестр не требуется.

Для каждой записи каталога предусматриваются:

- URL GitHub-репозитория;
- отображаемое имя;
- отдельный GitHub-токен для доступа к этому репозиторию (если он приватный);
- проверка доступа к репозиторию;
- удаление записи из каталога.

Каталог и связанные настройки должны сохраняться после перезапуска Home Assistant. Секреты хранятся на стороне Home Assistant/ESP32 Manager и не раскрываются в браузерном интерфейсе и не сохраняются в устройстве. Способ постоянного защищённого хранения токенов должен соответствовать API и рекомендациям Home Assistant; нельзя считать редактирование `secrets.yaml` обязательным или единственно допустимым решением.

### Выбор источника OTA

- В интерфейсе OTA добавляются выпадающий список репозиториев и выпадающий список релизов выбранного репозитория.
- Репозиторий и релиз выбираются для конкретного запуска OTA; устройство не получает постоянную привязку к ним.
- Для приватного репозитория используется credential соответствующей записи каталога.
- Ручной URL и ручной токен остаются доступными как альтернативный путь.
- Токен используется только для запросов к GitHub API. Его нельзя пересылать на внешний CDN-хост, с которого загружается бинарный файл.

## 7. Безопасность и совместимость

- Идентификатор физического устройства остаётся стабильным при смене прошивки.
- Продуктовый профиль описывает приложение, а не аппаратную модель.
- GitHub credentials остаются в Home Assistant и не передаются в ESP32 сверх уже предусмотренного OTA-механизма авторизации.
- Передавать токен разрешено только соответствующему GitHub API; URL загрузки бинарного файла может вести на внешний CDN и не должен получать этот токен.
- Новые поля и возможности MQTT-контрактов должны вводиться с явной версией схемы и без нарушения существующих универсальных контрактов.

## 8. Реализация и проверки

Уже реализовано и проверено в экосистеме:

1. Публикация retained-профиля Xiaomi BLE Gateway с QoS 1 при MQTT connect/reconnect.
2. Обработка профиля специализированной интеграцией Xiaomi Sensor Manager.
3. Перевод сущностей в недоступное состояние при отсутствии/очистке профиля и восстановление по актуальному retained-сообщению.
4. Очистка retained-профиля ESP32 Manager перед OTA; на реальном устройстве проверены tombstone, OTA и публикация нового профиля после перезагрузки.

Дальнейшие проверки и развитие:

1. Полный сценарий смены двух разных продуктовых прошивок на одном физическом ESP32, включая возврат к исходной прошивке.
2. Проверка отсутствия дубликатов устройств и сущностей после смены профиля и перезапуска Home Assistant.
3. Реализация каталога репозиториев и выбора релизов в ESP32 Manager согласно разделу 6.
4. Тестирование доступа к публичным и приватным репозиториям, хранения credentials и корректной загрузки OTA-артефактов.

Внутренние API, компоненты и правила разработки ESP32 Platform Core документируются в репозитории [esp32-platform-core](https://github.com/lavrenovalexsandr-cmyk/esp32-platform-core).
