# Архитектура экосистемы ESP32: ESP32 Manager, профили и межинтеграционный контракт

**Назначение:** единый межпроектный архитектурный документ экосистемы ESP32. Он описывает контракты и границы ответственности между прошивками, ESP32 Manager и специализированными интеграциями Home Assistant. Внутреннее устройство ESP32 Platform Core описывается отдельно в его репозитории.

**Статус:** MQTT-профиль версии 1, базовая идентификация устройств, availability, универсальный OTA и каталог репозиториев реализованы в текущей версии ESP32 Manager. Централизованный реестр, обязательная зависимость специализированных интеграций, публичный API операций и каскадное удаление описаны как целевая архитектура и не считаются реализованными до внесения кода и прохождения проверок.

## 1. Назначение и модель устройства

В экосистеме могут существовать независимые прошивки ESP32: BLE-шлюзы, контроллеры ворот, освещения и другие продукты. ESP32 Manager управляет физическими ESP32 независимо от назначения и установленной прошивки. Специализированные интеграции Home Assistant работают только с устройствами, подходящими для соответствующего продукта.

Различаем три понятия:

- **Физическое устройство** — конкретная ESP32 с постоянной аппаратной/платформенной идентичностью. OTA-перепрошивка не меняет её идентификатор.
- **Продуктовый профиль** — тип приложения, которое в данный момент работает на устройстве.
- **Возможности (capabilities)** — функции, которые объявляет конкретная прошивка.

Профиль не является аппаратной моделью. Не следует подменять им manufacturer или model физического устройства в Home Assistant.


## 2. Границы ответственности

### ESP32 Platform Core
- Универсальный платформенный слой прошивки: аппаратная идентичность, общие сервисы устройства, MQTT, availability, OTA и Factory Reset.
- Не содержит логики конкретных продуктов и не знает о Xiaomi, воротах, освещении и других прикладных функциях.
- Не ведёт реестр допустимых product_id или capabilities.

### Прикладная прошивка ESP32
- Определяет собственные product_id, capabilities и поддерживаемые операции.
- Является источником истины для фактического профиля и доступности операций.
- Публикует identity, availability и профиль по общим MQTT-контрактам.
- Принимает команды только в рамках реализованных возможностей и повторно проверяет входные параметры.
- После OTA публикует профиль новой прошивки; аппаратный device_id не меняется.
- Реализует Factory Reset по общим требованиям Core.

### ESP32 Manager — центральная интеграция-платформа
ESP32 Manager является обязательной базовой интеграцией для специализированных ESP32-интеграций Home Assistant и единственным центральным источником сведений об ESP32.

Он отвечает за:
- обнаружение и регистрацию физических ESP32, включая устройства без известного профиля;
- единый реестр устройств и общую идентичность, пользовательское имя, модель, версию прошивки, availability, профиль и capabilities;
- создание и сопровождение общей записи физического устройства в Home Assistant Device Registry;
- обработку общих MQTT identity, profile, availability и системных статусов;
- публичный API и события жизненного цикла для интеграций-потребителей;
- проверку доступности операций по профилю и маршрутизацию команд;
- универсальное управление, OTA, перезагрузку и Factory Reset;
- каскадное удаление устройства и координацию очистки данных потребителей;
- каталог GitHub-репозиториев прошивок и credentials.

ESP32 Manager не реализует прикладную логику Xiaomi, ворот, освещения и других продуктов. Он знает об операциях через декларативный контракт прошивки, но не содержит обработчики конкретных доменных данных.

### Специализированные интеграции Home Assistant
Примеры: Xiaomi Sensor Manager и будущие интеграции управления светом, воротами и другими устройствами.

- Обязательно объявляют ESP32 Manager в manifest.json как зависимость Home Assistant.
- Не обнаруживают ESP32 самостоятельно и не создают собственный реестр шлюзов.
- Не подписываются самостоятельно на общие MQTT-топики identity, profile и availability.
- Получают общие сведения об устройствах из публичного API ESP32 Manager и используют его события.
- Создают только собственные доменные сущности и хранят только собственные доменные данные.
- Не дублируют имя шлюза, модель, версию прошивки, профиль, availability и другие общие метаданные.
- Не импортируют Python-модули других специализированных интеграций и не связываются друг с другом напрямую.
- Выполняют поддерживаемые устройством операции через API/сервисы ESP32 Manager.
- Регистрируют обработчик удаления, чтобы Manager мог запросить полную очистку принадлежащих интеграции данных.

Специализированная интеграция может подписываться на собственные продуктовые MQTT-топики телеметрии и доменных данных. Общие identity/profile/availability принадлежат ESP32 Manager.

### Принцип единого источника истины
Для каждого физического устройства существует одна общая запись ESP32 Manager. Остальные интеграции ссылаются на неё по стабильному device_id и добавляют собственные сущности к той же записи Home Assistant.

Общая запись шлюза использует единый identifier:

```python
identifiers={("esp32", device_id)}
```

Пользовательское имя хранится в Home Assistant Device Registry в поле name_by_user. ESP32 Manager отвечает за первоначальную регистрацию; остальные интеграции используют общую запись и не заводят собственное имя шлюза.

## 3. MQTT-контракт продуктового профиля

Отдельный топик профиля не изменяет существующую аппаратную идентификацию в `device/info`:

```text
esp32/<DEVICE_ID>/device/profile
```

Сообщение публикуется в JSON, с QoS 1 и retain=true. Схема версии 1:

```json
{
  "schema_version": 1,
  "product_id": "xiaomi_ble_gateway",
  "firmware_version": "2.0.0",
  "capabilities": [
    "ble_gateway",
    "xiaomi_lywsd03"
  ]
}
```

Обязательные поля:

- `schema_version` — версия формата сообщения.
- `product_id` — стабильный идентификатор продукта, задаваемый прикладной прошивкой.
- `firmware_version` — версия работающей прикладной прошивки; должна совпадать со значением `sw_version` в `device/info`.
- `capabilities` — массив строк с возможностями прошивки. Пустой массив допустим.

Примеры идентификаторов (не закрытый реестр):

| Прошивка | product_id | capabilities |
|---|---|---|
| Xiaomi BLE Gateway | `xiaomi_ble_gateway` | `ble_gateway`, `xiaomi_lywsd03` |
| Gate Controller | `gate_controller` | `gate_control` |
| Light Controller | `light_controller` | `light_control`, `dimming` |

### Публикация и жизненный цикл

- Прошивка публикует актуальный профиль при первом подключении к MQTT и повторно после каждого MQTT reconnect.
- Профиль публикуется как retained-сообщение с QoS 1.
- Перед OTA ESP32 Manager публикует пустое retained-сообщение в `esp32/<DEVICE_ID>/device/profile` (MQTT tombstone).
- После успешной загрузки новая прошивка публикует свой профиль.
- Если новая прошивка не запускается и устройство загружает прежнюю прошивку, прежняя прошивка при старте/reconnect публикует свой профиль снова.
- Устройство без продуктового профиля не публикует сообщение профиля; отсутствие retained-сообщения означает отсутствие известного профиля.

### Валидация

- Неизвестный `schema_version`, некорректный JSON или отсутствие обязательных полей — профиль не используется.
- Несовпадение `firmware_version` и `sw_version` из `device/info` означает, что профиль неактуален и не должен использоваться до получения согласованных метаданных.
- Неизвестный `product_id` игнорируется интеграциями, которые его не поддерживают.
- Неизвестная отдельная capability не должна мешать обработке других поддерживаемых возможностей.


## 4. Смена профиля, жизненный цикл и сущности Home Assistant

Смена профиля не меняет идентификатор физической ESP32 и не удаляет общую запись устройства в Device Registry.

ESP32 Manager отслеживает текущий профиль и публикует обновления через общий API и событие изменения устройства. Специализированные интеграции не читают MQTT-профиль напрямую.

При смене профиля:
- Интеграция, возможности которой больше не объявлены устройством, переводит свои продуктовые сущности в недоступное состояние.
- Интеграция, которой соответствует новый профиль/capabilities, получает обновление от ESP32 Manager и создаёт или обновляет свои сущности.
- При возврате прежнего профиля соответствующая интеграция восстанавливает доступность сущностей.
- Обычная смена профиля не удаляет сущности. Удаление относится к отдельной операции полного удаления устройства.
- Временное отсутствие профиля, в том числе очистка retained-профиля перед OTA, означает неизвестный профиль и недоступность зависящих от него сущностей, а не удаление устройства.

### События жизненного цикла
Публичный контракт ESP32 Manager должен предоставлять как минимум следующие события:

| Событие | Назначение |
|---|---|
| esp32_ota_device_added | Устройство зарегистрировано или обнаружено повторно |
| esp32_ota_device_updated | Изменились метаданные, availability, профиль или capabilities |
| esp32_ota_device_removing | Начата согласованная операция удаления |
| esp32_ota_device_removed | Удаление завершено на стороне ESP32 Manager |

Каждое событие содержит стабильный device_id. Для добавления/обновления дополнительно передаётся актуальный snapshot устройства. Для удаления передаётся идентификатор и контекст операции.

События не заменяют получение начального состояния: при запуске специализированная интеграция получает список известных устройств из реестра ESP32 Manager, затем принимает события изменений. Повторная обработка snapshot/event должна быть безопасной и не создавать дубликатов.

### Идентичность и имя в Home Assistant
- Общая запись шлюза использует identifier ("esp32", device_id).
- ESP32 Manager отвечает за создание общей записи и обновление технических данных.
- Пользовательское имя name_by_user не перезаписывается исходным MQTT-именем.
- Специализированные интеграции привязывают свои устройства/сущности к общей записи через via_device и не создают альтернативные записи шлюза.
- Переименование шлюза выполняется средствами Home Assistant и отражается во всех интеграциях, использующих общую запись.

### Разделение данных
ESP32 Manager хранит общие данные физического устройства. Специализированные интеграции хранят только собственные данные: например, Xiaomi Sensor Manager — MAC-адреса датчиков, пользовательские имена, привязки, измерения и собственные настройки. Общие сведения о шлюзе в их persistent storage не дублируются.


## 5. Обнаружение и хранение профиля в Home Assistant

### Источники данных
- MQTT identity, availability и profile принимаются и обрабатываются ESP32 Manager.
- Retained-сообщение esp32/<DEVICE_ID>/device/profile остаётся источником истины на стороне устройства о текущем продуктовом профиле.
- ESP32 Manager преобразует MQTT-сообщения в единый нормализованный snapshot и предоставляет его потребителям через публичный API.
- Специализированные интеграции не интерпретируют общие MQTT-сообщения повторно и не ведут независимый runtime-кэш профилей.

### Публичный API ESP32 Manager
Целевая реализация предоставляет API через согласованный объект в hass.data, события Home Assistant и сервисы ESP32 Manager. Это публичный межинтеграционный контракт, а не внутренний модуль Python.

Логическое пространство публичного API: hass.data["esp32_ota"]["api"]. API version 1 реализован в ESP32 Manager.

API должен предоставлять:
- версию контракта API;
- получение snapshot одного устройства по device_id;
- получение списка известных устройств;
- регистрацию и снятие обработчиков жизненного цикла/удаления;
- проверку доступности объявленной операции;
- выполнение операции через ESP32 Manager.

Специализированные интеграции не импортируют Python-код ESP32 Manager или друг друга. Они обращаются к опубликованному API по документированному интерфейсу и проверяют поддерживаемую версию контракта.

### Минимальная модель snapshot устройства

| Поле | Назначение |
|---|---|
| device_id | Стабильный аппаратный идентификатор ESP32 |
| name | Исходное техническое имя устройства |
| name_by_user | Пользовательское имя из Device Registry, если задано |
| manufacturer | Производитель физического устройства |
| model | Аппаратная модель |
| sw_version | Версия установленной прошивки |
| available | Текущее MQTT availability |
| profile | Нормализованный профиль или null |
| product_id | Идентификатор текущего продукта или null |
| capabilities | Набор объявленных возможностей |
| operations | Набор объявленных поддерживаемых операций |

Профиль и operations могут отсутствовать у неизвестных/старых прошивок. Это не препятствует регистрации физического устройства и универсальному OTA.

### Правила хранения
- ESP32 Manager — единственный владелец общего runtime-реестра устройств.
- Специализированные интеграции не сохраняют копии общих метаданных и не создают независимые реестры шлюзов.
- Persistent storage потребителя содержит только данные его предметной области.
- Device Registry хранит общую физическую идентичность; Entity Registry — сущности соответствующих интеграций.
- После перезапуска ESP32 Manager восстанавливает состояние из retained MQTT; потребители получают актуальный snapshot через API.
- При потере MQTT-соединения ESP32 Manager обновляет availability и уведомляет потребителей.
- При получении tombstone профиля ESP32 Manager очищает профиль в snapshot и уведомляет потребителей. Записи устройства и сущностей не удаляются.
- Повторные retained-сообщения и reconnect не должны создавать дубликаты.

## 6. Универсальный OTA и каталог репозиториев

### Общие правила

ESP32 Manager должен позволять выбрать для любого обнаруженного устройства любой репозиторий и любой доступный релиз прошивки.

- Выбор репозитория и релиза относится к текущей операции OTA и не закрепляется за устройством как постоянное назначение.
- Несовпадение `product_id` текущей прошивки и устанавливаемой прошивки не блокирует OTA. Допустимо показать предупреждение, но не запрещать установку.
- Автоматическая фильтрация репозиториев или релизов по `product_id` не выполняется.
- При выборе релиза ESP32 Manager получает URL подходящего OTA-артефакта и подставляет его в существующее поле URL прошивки.
- Существующее поле URL остаётся доступным для ручного ввода и прямого OTA без выбора релиза.
- Существующие поля и сценарии OTA, включая ручной ввод GitHub-токена, сохраняются.

### Каталог репозиториев

Каталог ведётся локально в конкретной установке Home Assistant; централизованный общий реестр не требуется.

Для каждой записи каталога предусматриваются:

- URL GitHub-репозитория;
- отображаемое имя;
- отдельный GitHub-токен для доступа к этому репозиторию (если он приватный);
- проверка доступа к репозиторию;
- удаление записи из каталога.

Каталог и связанные настройки должны сохраняться после перезапуска Home Assistant. Секреты хранятся на стороне Home Assistant/ESP32 Manager и не раскрываются в браузерном интерфейсе и не сохраняются в устройстве. Способ постоянного защищённого хранения токенов должен соответствовать API и рекомендациям Home Assistant; нельзя считать редактирование `secrets.yaml` обязательным или единственно допустимым решением.

### Выбор источника OTA

- В интерфейсе OTA добавляются выпадающий список репозиториев и выпадающий список релизов выбранного репозитория.
- Репозиторий и релиз выбираются для конкретного запуска OTA; устройство не получает постоянную привязку к ним.
- Для приватного репозитория используется credential соответствующей записи каталога.
- Ручной URL и ручной токен остаются доступными как альтернативный путь.
- Токен используется только для запросов к GitHub API. Его нельзя пересылать на внешний CDN-хост, с которого загружается бинарный файл.


## 7. Команды, операции и расширение профиля

### Разделение capabilities и operations
Capabilities описывают функциональные области прошивки: например, ble_gateway, xiaomi_lywsd03, gate_control, light_control.

Operations описывают конкретные действия, которые ESP32 Manager может запросить у устройства. Наличие capability само по себе не является достаточным описанием команды и её параметров.

Профиль должен постепенно развиваться от списка возможностей к декларативному контракту операций. Пример целевого расширенного профиля:

```json
{
  "schema_version": 2,
  "product_id": "light_controller",
  "firmware_version": "2.0.0",
  "capabilities": ["light_control", "dimming"],
  "operations": {
    "light.set": {
      "title": "Управление освещением",
      "description": "Установка состояния и яркости канала",
      "parameters": {
        "type": "object",
        "properties": {
          "channel": {"type": "integer", "minimum": 0},
          "state": {"type": "boolean"},
          "brightness": {"type": "integer", "minimum": 0, "maximum": 100}
        },
        "required": ["channel", "state"],
        "additionalProperties": false
      }
    }
  }
}
```

Это иллюстрация целевой схемы, а не описание уже реализованного формата. До выпуска schema v2 необходимо отдельно согласовать JSON Schema, правила совместимости и формат результата операции.

### Правила выполнения операций
- Специализированная интеграция обращается к ESP32 Manager с device_id, operation_id и параметрами.
- Manager проверяет, что устройство известно, доступно и объявляет указанную операцию в актуальном профиле.
- Manager валидирует параметры по схеме операции и только после этого отправляет команду.
- Прошивка повторно валидирует параметры; проверка в Home Assistant не заменяет проверку на устройстве.
- Manager нормализует результат и передаёт его вызывающей интеграции.
- Если операция не объявлена, профиль неизвестен или параметры не проходят проверку, команда не отправляется.
- Специализированные интеграции не формируют общие MQTT-команды самостоятельно и не обходят проверку Manager.

### Транспорт команд
Целевой общий транспорт для новых операций — адресная команда с JSON payload и отдельным результатом. Идентификатор операции является частью контракта. MQTT-топики, QoS, retain, correlation ID, timeout, retry и схема результата должны быть зафиксированы в версии протокола до реализации.

Существующие команды system/restart, system/factory_reset и ota/update сохраняются как действующий совместимый контракт. Новые интеграции используют для них ESP32 Manager.

### Обратная совместимость
- Профиль schema v1 остаётся поддерживаемым.
- Устройства без operations продолжают обнаруживаться и управляться базовыми возможностями ESP32 Manager.
- Неизвестные поля и capabilities не должны ломать обработку известных данных.
- Переход к schema v2 выполняется поэтапно; одновременное обновление всех прошивок и интеграций не требуется.
- До внедрения общего контракта операций существующие продуктовые MQTT-команды не считаются автоматически доступными через новый API.

## 8. Полное удаление физического устройства

Полное удаление запускается стандартным действием Home Assistant «Удалить устройство» для общей записи ESP32, а также может быть вызвано сервисом ESP32 Manager. Это не то же самое, что удаление отдельного датчика или прикладной сущности внутри специализированной интеграции.

### Последовательность удаления
1. ESP32 Manager переводит устройство в состояние removing и прекращает принимать для него обычные обновления в рамках текущей операции.
2. Manager отправляет Factory Reset только если устройство в этот момент доступно по MQTT.
3. Если устройство доступно, команда публикуется адресно с QoS 1 и без retain. Успешная публикация подтверждает только передачу команды брокеру, но не завершение физического сброса.
4. Если устройство недоступно, команда Factory Reset не отправляется. Запрос не сохраняется, не ставится в очередь и не повторяется при последующем подключении. Отложенные задания физического сброса запрещены.
5. Manager вызывает зарегистрированные обработчики удаления специализированных интеграций. Каждый обработчик очищает все принадлежащие ему данные для device_id.
6. Manager очищает собственные runtime-данные и известные retained MQTT-сообщения устройства. Потребители очищают принадлежащие им retained-топики в своих обработчиках.
7. Manager удаляет общую запись и связанные общие сущности/записи Home Assistant Registry.
8. Операция завершается и публикуется событие esp32_manager_device_removed.

### Что очищает специализированная интеграция
Обработчик удаления удаляет все данные, связанные с указанным шлюзом, включая при наличии:
- собственные HA entities и child devices;
- привязки датчиков/исполнительных устройств к шлюзу;
- пользовательские имена;
- persistent storage и локальные реестры;
- runtime-кэши и временные операции;
- pending-команды и результаты;
- tombstones, относящиеся к удаляемому шлюзу;
- принадлежащие интеграции retained MQTT-сообщения.

Очистка одного шлюза не должна затрагивать данные других ESP32.

### Обработчики удаления и ошибки
- Специализированные интеграции регистрируют асинхронный обработчик удаления в публичном API при загрузке и снимают регистрацию при выгрузке.
- Manager ожидает завершения обработчиков до удаления общей записи устройства.
- Ошибка одного обработчика логируется с указанием интеграции и device_id; остальные обработчики всё равно вызываются.
- Ошибка очистки не должна приводить к молчаливому восстановлению старых данных при повторном обнаружении. Должна быть доступна диагностика частично завершившейся очистки.
- Повторная очистка должна быть безопасной: отсутствие уже удалённых записей не считается ошибкой.
- Если потребитель не загружен или не зарегистрировал обработчик, полная очистка его данных не гарантируется. Поэтому зависимость от Manager и корректная регистрация обработчиков обязательны.

### MQTT и повторное обнаружение
- Удаление очищает известные retained-сообщения устройства, включая identity и profile, а также retained-сообщения, зарегистрированные специализированными интеграциями.
- Каждый компонент, создающий retained-топики, обязан документировать их и обеспечивать очистку при удалении.
- Старые retained-сообщения не должны немедленно воссоздавать прежнее состояние.
- Если физическая ESP32 была офлайн, она не получила Factory Reset и физически не очищена. Если позднее она подключится и опубликует identity, Manager может обнаружить её заново с тем же аппаратным device_id; данные интеграций к этому моменту должны быть очищены.
- Отложенный Factory Reset, persistent wipe request, очередь сбросов и автоматическая отправка сброса при reconnect запрещены.
- Удаление в Home Assistant не блокирует обычное последующее обнаружение устройства, если оно снова объявит себя по MQTT.

## 9. Реализация и проверки

Уже реализовано и проверено в экосистеме:

1. Публикация retained-профиля Xiaomi BLE Gateway с QoS 1 при MQTT connect/reconnect.
2. Обработка профиля специализированной интеграцией Xiaomi Sensor Manager.
3. Перевод сущностей в недоступное состояние при отсутствии/очистке профиля и восстановление по актуальному retained-сообщению.
4. Очистка retained-профиля ESP32 Manager перед OTA; на реальном устройстве проверены tombstone, OTA и публикация нового профиля после перезагрузки.

Дальнейшие проверки и развитие:

1. Полный сценарий смены двух разных продуктовых прошивок на одном физическом ESP32, включая возврат к исходной прошивке.
2. Проверка отсутствия дубликатов устройств и сущностей после смены профиля и перезапуска Home Assistant.
3. Проверка на реальном Home Assistant каталога репозиториев и выбора релизов, включая сохранение credentials после перезапуска.
4. Тестирование доступа к публичным и приватным репозиториям и OTA-загрузки выбранных артефактов.
5. Реализация центрального реестра ESP32 Manager и публичного API snapshot устройств.
6. Перевод Xiaomi Sensor Manager на обязательную зависимость от ESP32 Manager: убрать собственное обнаружение шлюзов и обработку общих identity/profile/availability.
7. Реализация событий жизненного цикла и проверка восстановления состояния потребителей после перезапуска Home Assistant.
8. Реализация общего контракта операций и постепенное расширение профиля до декларативного описания параметров и результатов команд.
9. Реализация каскадного удаления через стандартное действие Home Assistant и проверка очистки данных XSM, включая дочерние устройства, имена, привязки и persistent storage.
10. Проверка удаления доступной и недоступной ESP32. Для недоступной ESP32 должно быть подтверждено отсутствие отложенной команды Factory Reset.
11. Проверка повторного обнаружения после удаления и отсутствие восстановления старых данных.

Внутренние API, компоненты и правила разработки ESP32 Platform Core документируются в репозитории [esp32-platform-core](https://github.com/lavrenovalexsandr-cmyk/esp32-platform-core).


## 10. Правила расширения экосистемы

При добавлении нового продукта или специализированной интеграции:

1. Новая прошивка использует общие механизмы идентификации, availability, OTA и Factory Reset из ESP32 Platform Core.
2. Прошивка объявляет стабильный product_id, capabilities и поддерживаемые операции в продуктовом профиле.
3. ESP32 Manager остаётся единственной интеграцией, которая обнаруживает физическое устройство и ведёт его общую запись.
4. Новая специализированная интеграция объявляет ESP32 Manager обязательной зависимостью в manifest.json.
5. Интеграция получает устройства и общие метаданные из публичного API Manager; не подписывается на общие MQTT-топики и не создаёт собственный реестр шлюзов.
6. Интеграция хранит только свои прикладные данные и создаёт собственные сущности, привязанные к общей записи ESP32.
7. Команды выполняются через общий API операций после проверки capability/operation и параметров.
8. Интеграция реализует и регистрирует обработчик полного удаления своих данных.
9. В документации продукта фиксируются MQTT-топики, capabilities, операции, схемы параметров/результатов, retained-сообщения и правила очистки.
10. Интеграция проходит проверки добавления, обновления, offline/online, смены прошивки/профиля, перезапуска Home Assistant, удаления шлюза и повторного обнаружения.

Новая специализированная интеграция не должна создавать прямую зависимость от другой специализированной интеграции. Все общие зависимости проходят через ESP32 Manager.

## 11. Текущее состояние реализации и целевая архитектура

Документ фиксирует целевую архитектуру. На момент обновления в коде ESP32 Manager уже реализованы MQTT discovery по device/info, availability, OTA status, OTA, restart, Factory Reset, очистка retained-профиля перед OTA, общий identifier ("esp32", device_id) и каталог репозиториев.

В текущих ветках реализации добавлены публичный API version 1, snapshots, события added/updated/removing/removed и регистрация cleanup handlers. Xiaomi Sensor Manager переведён на обязательную зависимость от ESP32 Manager и получает общие identity/profile/availability только через публичный API. Продуктовые Xiaomi MQTT-топики остаются в XSM.

Каскадное удаление через сервис и стандартный callback Device Registry реализовано в ESP32 Manager. Factory Reset отправляется только если устройство доступно; отложенная очередь сбросов отсутствует.

До слияния и сквозной проверки обеих веток на реальном Home Assistant миграцию нельзя считать завершённой. Декларативный контракт operations и маршрутизация специализированных команд через общий API остаются следующими отдельными этапами.
